## Problem Statement

Build a technically trustworthy support agent for a complex physical product. The agent must answer questions from the Vulcan OmniPro 220 manuals, recognize when the answer depends on visual evidence, ask for missing context when a question is ambiguous, and turn hard explanations into diagrams or interactive tools. A reviewer must be able to clone the repository, add one Anthropic key, and reach a convincing answer in under two minutes.

The assessment is not won by a generic chat interface. It is won when a reviewer asks a hard question and sees the agent retrieve the right manual evidence, reason across it, communicate safely, and present the answer in the format that is easiest to use beside the machine.

## What Makes This Cool

ArcLens behaves like a field technician who can draw. It does not merely cite page 13 for polarity. It renders the two sockets, places the ground clamp and torch or feeder cable in the correct ports, labels DCEN or DCEP, and keeps the supporting manual page one click away. It does not merely repeat the duty-cycle paragraph. It turns amperage and input voltage into a ten-minute work/rest timeline. It does not dump a porosity checklist. It asks whether the user is running gas-shielded MIG or gasless flux-core, then walks the relevant diagnostic branch while showing the weld-defect reference.

The core capability generalizes beyond this welder: convert dense, mixed-format product documentation into evidence-backed, generated interfaces that reduce cognitive load at the moment of work.

## Constraints

- The agent foundation must be `@anthropic-ai/claude-agent-sdk`.
- Local startup must require only `ANTHROPIC_API_KEY`, package installation, and one dev command.
- Evaluators may ask questions whose answers require multiple pages, diagrams, tables, or clarification.
- Critical facts must come from the provided files. The model must not improvise settings or safety advice.
- Visual evidence must remain attributable to its source document and page.
- The UI must support useful loading, partial, empty, clarification, error, and retry states.
- Pre-generated knowledge assets must be committed so evaluators do not need Poppler, OCR, or an ingestion service.
- Runtime tools must be read-only and narrowly scoped to the bundled knowledge base.
- The app must remain useful on a laptop and a phone in a workshop environment.

## Premises

1. **Reliability beats unconstrained novelty.** Prox says it will test the agent hard. A small set of typed, interactive artifact primitives is more dependable than arbitrary model-generated JavaScript while still demonstrating code generation as a product primitive.
2. **Page images are first-class knowledge.** The image-only selection chart, weld profiles, polarity diagrams, and wiring schematic cannot be reduced to text without losing important information. Retrieval must return both normalized text and visual page evidence.
3. **The Agent SDK should orchestrate domain tools, not receive unrestricted machine access.** The agent gets manual search, page inspection, structured product facts, and artifact-presentation tools. It does not get Bash, file writes, or web access.
4. **Deterministic facts should be represented deterministically.** Polarity, rated duty cycles, process capabilities, and diagnostic steps are normalized into tested product data. Claude uses them with retrieved manual passages rather than reconstructing every value from scratch.
5. **Ambiguity is a product state, not an error.** The assistant must ask for process, input voltage, material, or observed symptom when those details change the answer.
6. **Voice is polish, not the proof.** Browser push-to-talk and read-aloud can be added after the evidence and artifact paths are correct. A flashy voice layer cannot compensate for a wrong technical answer.

## Approaches Considered

### Approach A: Evidence-first artifact workbench

A single Next.js application runs the Claude Agent SDK on the server. An in-process MCP server exposes narrowly scoped tools for hybrid manual search, page evidence, verified product facts, and typed artifact emission. The frontend streams the reasoning result and renders artifact payloads as purpose-built React experiences.

- Effort: L
- Risk: Medium
- Strengths: strongest technical accuracy, explicit Agent SDK use, rich multimodality, testable artifact contracts, simple evaluator setup.
- Costs: requires an ingestion pipeline, several renderers, and careful stream/event handling.
- Reuses: provided manuals and images, Agent SDK in-process MCP tools, native browser audio APIs for optional voice.

### Approach B: Free-form generated mini-apps

Give the model a code-generation tool and render arbitrary HTML, CSS, and JavaScript in a sandboxed iframe for each answer.

- Effort: XL
- Risk: High
- Strengths: closest to open-ended Claude Artifacts and can produce surprising interfaces.
- Costs: hard to secure, hard to test, visually inconsistent, slower, and likely to fail adversarial evaluation on malformed or unsafe output.
- Reuses: Agent SDK and a generic artifact sandbox.
- Decision: rejected as the primary path. A typed artifact grammar provides most of the value with much better reliability.

### Approach C: Minimal multimodal chat

Use manual text retrieval plus a chat UI that can attach static page images.

- Effort: M
- Risk: Low
- Strengths: fast to ship and easy to understand.
- Costs: misses the challenge's strongest instruction: generate diagrams and interactive content when text is cognitively expensive.
- Decision: rejected because it would look like a competent baseline rather than a founding-engineer submission.

### Knowledge package

- Extract every owner-manual page into layout-preserving text.
- Render every page to a web-friendly image and retain original PDF links.
- Add the quick-start guide and image-only selection chart as separate sources.
- Generate a checked-in manifest containing a canonical source identity, section, text, image path, safety flag, and manually curated tags.
- Normalize evaluator-critical product facts into typed data with exact source references.
- Use a small local BM25-style lexical ranker plus tag and phrase boosts. The corpus is tiny; an external vector database would add setup friction without improving the demo enough.

Every citation uses the same `SourceRef` shape:

```ts
type SourceRef = {
  id: `${string}:pdf-${number}`;
  documentId: "owner-manual" | "quick-start" | "selection-chart";
  pdfPageNumber: number; // explicit one-based page number in the PDF file
  printedPageLabel: string | null;
  section: string;
  assetUrl: string;
  region?: { x: number; y: number; width: number; height: number };
};
```

The one-based PDF page number is the machine lookup key. The printed page label is display metadata. Facts, search results, artifacts, citations, and tests store the complete reference rather than passing around bare page numbers. Boundary tests cover the first and last page of every document and reject page zero.

Image-heavy pages also receive checked-in, human-verified `VisualEvidence` records containing a caption, entities, relationships, labeled regions, aliases, and likely user intents. For example, the wiring schematic is searchable by `wiring`, `MCU board`, `remote board`, `fan`, `solenoid`, and `rectifier`, while the selection chart is searchable by process, gas, skill level, material, thickness, and cleanliness. Ranking indexes this catalog beside extracted text.

The generated knowledge directory includes source SHA-256 checksums and a generator version. `npm run knowledge:check` validates every manifest entry and schema, verifies checksums, detects missing and orphaned page assets, checks unique source IDs, asserts required product facts, and fails when checked-in output is stale relative to the source PDFs. Regeneration is deterministic and available through `npm run knowledge:build`; reviewers do not need it because verified outputs are committed.

### Agent tools

- `search_manual`: ranked evidence with source, page, excerpt, and visual availability.
- `get_manual_pages`: full page records and image URLs for evidence inspection.
- `get_product_fact`: deterministic polarity, duty-cycle, process, and safety facts.
- `present_artifact`: validates and emits one typed artifact payload.
- `submit_answer`: the only valid completion path; submits a typed answer, clarification, or abstention envelope.

The SDK configuration is part of the safety contract, not an implementation detail:

- `allowedTools` contains only the five in-process MCP tools, using their fully qualified names.
- Built-in `Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`, web, and subagent tools are absent.
- `permissionMode` is non-interactive and tool approval fails closed.
- `cwd` points to an empty temporary directory with no product files or secrets.
- Each turn has a maximum of 8 agent turns, a 45-second wall timeout, request cancellation, and a configurable USD budget ceiling that defaults to a low demo-safe value.
- Startup assertions and tests verify that the effective allowlist contains no built-in tools.
- The default model is the pinned `claude-sonnet-5-5` ID at `high` effort, selected for the best speed/intelligence balance in an interactive demo. `CLAUDE_MODEL` and `CLAUDE_EFFORT` are explicit overrides. The resolved values appear in health output, usage summaries, and eval reports. Model-access errors are actionable and never trigger a silent fallback.

`submit_answer` accepts a discriminated envelope. An answer contains user-facing prose plus atomic claims, and every technical claim names canonical source IDs, transformation type, safety class, and dependent artifact element IDs. Clarification and abstention are separate variants. The tool validates shape, source existence, deterministic facts, and safety requirements before storing the envelope in the request collector. Free-form SDK final output is ignored; if no valid envelope arrives, one bounded repair turn asks Claude to call `submit_answer`, then the server emits a safe retryable error.

### Artifact grammar

- Polarity connection diagram with sockets, cables, process, DCEN/DCEP, and source page.
- Duty-cycle timeline/calculator with welding and rest segments.
- Troubleshooting decision flow with clarifying branches and check-off steps.
- Settings/process configurator based on input voltage, process, material, thickness, wire, and gas.
- Manual evidence viewer with page image, source label, and relevant callout.
- Weld-defect comparison gallery using the diagnosis pages.

Every artifact includes `title`, `summary`, `sources`, and typed data. The server rejects malformed payloads. The UI never executes model-written JavaScript.

This still demonstrates code generation as a primitive: Claude composes a small declarative artifact program at runtime from visual primitives, controls, branches, annotations, and source-bound data. The React interpreter executes that validated program. It is not a prompt-to-widget lookup; a single troubleshooting program can contain novel branch order, condition labels, evidence callouts, and user controls while remaining inside a safe grammar. Tests require a novel composition whose structure is not present in a canned example.

Artifact handling is fail-soft. The server permits at most two artifact emissions per answer and assigns stable IDs. A later emission with the same ID replaces the earlier version; a new ID appends. Invalid, conflicting, over-limit, or unknown-version payloads never erase the text answer. The client shows a recoverable “visual could not be rendered” notice with the cited sources, and the server records a redacted validation error. No-artifact answers remain valid only when the response contract classifies text as sufficient.

`present_artifact` validates and normalizes its input inside the request process, assigns a server ID, and records the artifact in a request-scoped event collector keyed by Agent SDK tool-call ID. It returns only a small receipt to Claude (`accepted`, server ID, source count). After the SDK accepts the tool result, the HTTP producer drains that collector once. Replayed tool calls with the same request/tool-call key return the existing receipt and do not emit twice.

The settings configurator is limited to exact combinations represented in the corpus. Unsupported combinations return an explicit “not specified in the provided manuals” state and suggest the closest source page without extrapolating voltage, wire speed, gas, or thickness settings.

### Conversation and stream contract

The browser creates a UUID `conversationId`. The server stores only an in-memory mapping from that ID to the Agent SDK session ID and last activity time. Follow-ups resume the mapped session. Reset disposes the session and creates a new conversation. Idle sessions expire after 30 minutes. A process restart loses the mapping cleanly; the next request returns a typed `session_expired` error and the UI offers a bounded recovery payload containing prior user turns plus already validated answer envelopes and source IDs. Recovered assistant prose is context, never evidence; every new answer reruns retrieval. Cancellation aborts the SDK query, acknowledges completion to the client, and discards any incomplete artifact.

The API streams newline-delimited JSON using a versioned discriminated union:

```ts
type AgentEvent =
  | { v: 1; type: "start"; requestId: string; conversationId: string }
  | { v: 1; type: "status"; phase: "retrieving" | "reasoning" | "presenting" }
  | { v: 1; type: "answer"; text: string }
  | { v: 1; type: "sources"; sources: SourceRef[] }
  | { v: 1; type: "artifact"; operation: "append" | "replace"; artifact: Artifact }
  | { v: 1; type: "clarification"; question: string; choices?: string[] }
  | { v: 1; type: "done"; conversationId: string; usage: UsageSummary }
  | { v: 1; type: "cancelled"; requestId: string }
  | { v: 1; type: "error"; code: ErrorCode; message: string; retryable: boolean };
```

`start` is first and exactly one of `done`, `cancelled`, or `error` is terminal. Technical answer text is buffered server-side inside the structured answer envelope. The client receives status events while Claude works, then receives `sources`, validated artifacts, and one validated `answer` event. No technical claim is streamed before the grounding gate can accept it. Artifact operations follow the stable-ID rules above. Retrying creates a new request ID so terminal events and usage cannot be double-counted. The provider session ID never leaves the server.

Requests are serialized per conversation. A second send receives a retryable `conversation_busy` error rather than running concurrently. Cancel, reset, and expiry are idempotent state transitions. Cancellation wins only while the request is active; once `done` is committed, later cancellation is a no-op. Reset first cancels an active request, waits for its `cancelled` terminal state, disposes the provider session, and then acknowledges the reset. Expiry never interrupts an active turn; it is evaluated after the turn becomes idle. Reducer and integration tests cover overlapping send/send, send/cancel, cancel/done, reset/active, repeated cancellation, and expiry races.

### Trust and safety

- Put urgent safety conditions before procedural advice.
- Cite every concrete setting and connection claim.
- Say when the manuals do not contain enough information.
- Never infer live electrical measurements or tell users to service energized equipment.
- Limit agent tools to the bundled read-only corpus.
- Add request cancellation, timeouts, rate limiting, and human-readable error recovery.

Before a response reaches the UI, a grounding validator checks the structured answer envelope. Concrete settings, polarity, duty cycle, servicing, and safety claims must name source IDs returned by the tools. Polarity and rated-duty claims are cross-checked against deterministic facts. Safety-tagged retrieval results must be carried into any procedural answer that touches their subject. If evidence is missing or below the rank threshold, the only permitted outcomes are a clarification question or an explicit abstention. The final renderer derives citation labels from the canonical source records, never model-authored page strings.

### Presentation

- Workshop-console visual direction: warm off-white, charcoal, safety orange, instrument-panel typography, large touch targets, minimal chrome.
- Desktop: conversation and artifact canvas side by side.
- Mobile: conversation first, artifact opens as a full-width sheet.
- Landing state offers the three hard evaluator prompts plus a process-selection prompt.
- Evidence is visible without exposing chain-of-thought: show pages consulted, not hidden reasoning.

## Competitive Baseline and Winning Thesis

The public-fork audit covered all 158 accessible forks, identified 86 compare-confirmed code implementations, and deep-read the strongest submissions. The visible bar already includes large visual corpora, deterministic widgets, dynamic artifacts, browser voice, photo diagnosis, hosted demos, and serious eval suites. Details and primary-source links live in [the fork landscape](../research/fork-landscape.md) and [feature deep dive](../research/fork-feature-matrix.md).

ArcLens will match that reliability floor, then own four product capabilities the field largely leaves open:

### Verify before you act

The flagship flow is a camera-based setup preflight. The user chooses a task such as gasless flux-core setup, sees the source-backed expected configuration, and photographs the front panel and inside spool/cable area. Vision produces bounded observations with confidence, never facts. A deterministic verifier compares observed and expected states, overlays discrepancies on the photo, cites the exact manual regions behind each expected state, and refuses to issue a pass when the image cannot prove a condition. Only after verification does the product advance to a large-touch guided procedure.

### Proof Mode

Every answer compiles into an evidence ledger. Clicking a sentence, socket label, timer segment, or troubleshooting branch opens the exact source crop and shows whether it came from a deterministic lookup, arithmetic, visual extraction, comparison, or model synthesis. Proof Mode exposes validation outcomes and regression-case status without exposing chain-of-thought.

### Knowledge-gap correction loop

An insufficient-evidence outcome creates a structured gap containing the question, machine context, evidence searched, missing entity or relation, proposed technician question, and affected eval category. A small expert panel can add technician knowledge, bind it to evidence or mark it as field knowledge, keep it quarantined until verified, version the fact, and rerun only impacted evals.

### Exportable support case

Each troubleshooting session accumulates observations, checks, eliminated causes, safety stops, resolution, and evidence into an exportable case. When escalation is necessary, a human receives the full diagnostic record instead of asking the customer to start over.

## Success Criteria

### Technical accuracy

- Correctly answers that MIG/wire welding at 200 A on 240 VAC has a 25% rated duty cycle: 2.5 minutes welding and 7.5 minutes resting in each ten-minute period, citing owner-manual page 19.
- Diagnoses flux-cored porosity through the documented checks and correctly distinguishes DCEN for flux-core from DCEP for gas-shielded MIG, citing pages 13, 14, 37, and 43 as applicable.
- Shows TIG polarity with the ground clamp in the positive socket and TIG torch in the negative socket, citing owner-manual page 25.
- Asks a clarification question when process or input voltage changes the answer.

### Multimodality

- The three example questions produce three different useful artifact types.
- At least one response surfaces the exact manual page image.
- The selection chart and wiring schematic are discoverable despite having little or no extractable text.
- Artifacts are keyboard accessible, responsive, printable, and useful without animation.

### Evaluator experience

- Fresh clone to working local app in under two minutes after adding the API key.
- Clear `.env.example`, one install command, one run command, and an API-key health check.
- README explains architecture, knowledge extraction, artifact contracts, safety posture, tests, and tradeoffs.
- A scripted eval suite covers retrieval, deterministic facts, artifact validation, and representative end-to-end prompts.
- The repository includes a short demo script and recording checklist.

### Evaluation release gate

The blocking core eval corpus contains at least:

- 12 direct fact questions across processes, voltage, controls, and maintenance.
- 8 cross-page synthesis questions.
- 6 visual-only or visual-dominant retrieval questions.
- 6 ambiguous prompts that must clarify rather than guess.
- 6 safety or unsupported-service prompts that must warn or abstain.
- 2 cases for each of the four must-have artifact families, including one novel composition.
- Adversarial citation cases that mention misleading page numbers or incompatible processes.

An extended suite activates only for implemented should-have features such as the settings configurator, weld gallery, photo preflight, expert correction, voice, and support-case export. Submission readiness is controlled by the blocking core suite; a feature cannot be advertised unless its extended suite passes.

Offline tests cover ranking, source identity, checksums, normalized facts, grounding gates, event ordering, artifact schemas, fallback behavior, UI reducers, race contracts, and mutation failures with no API key. Live Agent SDK evals use at least 80 adversarial cases split into visible tuning and sealed holdout sets. Nondeterminism is tolerated through a rubric: technical fact accuracy 100% on deterministic facts, citation precision and recall at least 95%, required clarification at least 90%, safety/abstention 100%, valid artifact rate at least 95%, and zero unauthorized tool calls. The report preserves raw envelopes and records latency p50/p95 and cost per case. Submission is blocked unless all offline tests pass, every safety case passes, and the live holdout aggregate is at least 90% with no deterministic-fact failure. Mutation tests flip polarity, remove citations, corrupt page mapping, permit a built-in tool, and alter artifact values to prove the suite catches broken guards.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — feasibility

**Problem**

> The grounding gate relies on a structured answer envelope, but the four declared agent tools do not include an answer-submission tool and the design never defines an Agent SDK structured-output schema; an unrestricted final text result cannot be reliably decomposed into claims and source IDs for validation.

**Remedy**

> Define the exact final-answer production contract, such as a validated `submit_answer` MCP tool or supported structured output schema, with typed claims, source IDs, safety flags, clarification/abstention variants, and user-facing prose. Reject or repair free-form final output before any answer event is emitted.

### R3-2 — consistency

**Problem**

> The release corpus requires two cases for every artifact family while the Scope Boundary classifies the settings configurator and weld-defect gallery as should-have work that cannot start until the core gate passes; the stated submission gate therefore makes optional artifacts blocking before they exist.

**Remedy**

> Split evaluation into a blocking core suite for the four must-have artifact families and an extended suite enabled only for implemented should-have artifacts, or move all six families into must-have scope. State which suite controls submission readiness.

### R3-3 — clarity

**Problem**

> `SourceRef.pdfPageIndex` is the machine lookup key but its zero-based or one-based convention is unspecified, preserving an avoidable off-by-one risk at the page renderer boundary.

**Remedy**

> Name the convention in the type or field documentation, preferably use an explicit one-based `pdfPageNumber` for file-facing references, and add boundary tests for the first and last page of every document.

### R3-4 — completeness

**Problem**

> The design says a lost session restarts with the visible transcript summarized into a new request, but it does not define who creates that summary, what transcript subset is sent, or how technical claims in the summary avoid becoming ungrounded context for later answers.

**Remedy**

> Specify a bounded recovery payload that sends prior user turns plus already validated answer envelopes and source IDs, not a free-form client summary; re-run retrieval for new answers and never treat recovered assistant text as evidence.
